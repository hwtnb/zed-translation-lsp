# 対応言語

[English](../languages.md)

このページでは、ホバーでコメントを翻訳できる言語、コメントを抽出する規則と制約、言語ごとの言語サーバーの設定を説明します。

## 対応する言語

ホバーによる自動翻訳はRust、JavaScript／JSX、TypeScript／TSX、C#、C、C++、Python、Go、Ruby、PHP、HTML、CSS、JSON、JSONC、YAML、TOML、シェルスクリプト、PowerShell、Dockerfile、Docker Composeのコメントと、Pythonのドキュメンテーション文字列が対象です。Markdownは文章の選択後にバックグラウンド翻訳し、段落へのホバーだけでは開始しません。

## コメントの抽出

### 全般的な規則

サーバーは、文書を実行せず、その言語と同じように読んでコメントを見つけます。RustはRustコンパイラーの字句解析器、JavaScriptとTypeScriptはOxcの構文解析器、C、C++、C#、PythonはそれぞれのTree-sitterの文法、YAMLはYAMLのスキャナーで読みます。ほかの言語は、その言語の字句解析に従うサーバー独自の読み取りで読みます。文字列などのリテラルの中は、コメントとして扱いません。

連続する行の行コメントは、種類と字下げが同じで、どれもコードと同じ行にないとき、まとめて翻訳します。ブロックコメント、ドキュメンテーション文字列、HTMLのコメントは、1つずつ翻訳します。

書きかけの箇所や、サーバーがその言語と同じように読めない箇所では、次のどれかになります。どれが当てはまるかは、各言語の節で説明します。

- 閉じていないブロックコメントは、閉じるまで翻訳せず、それより後のコメントも見つけません。
- 閉じていない文字列などのリテラルは、その言語の読み方に従って、それより後のコメントを隠すか、その行の末尾で終わります。
- 構文エラーの周りや、その言語が複数の読み方をしうる箇所では、コメントを対象から外すか、そこで抽出を止めます。そこより前のコメントは抽出できます。
- RubyとHTMLの節で説明する書き方では、その言語がコメントとして読まない文字列をコメントとして扱うことがあります。

どの場合も、範囲を選択して `Translate selection to …` を使えば翻訳できます。

#### コメントを読み取れなかった文書

サーバーは、ホバーや翻訳で最初に必要になったときに文書のコメントを読み取り、編集のあとにもう一度読み取ります。C、C++、C#、Pythonでは、読み取りが `comment_parse_timeout_ms`（既定値は1秒）を超えると、そこで止めます。ほかの言語には、この上限はありません。

読み取りが上限で止まった場合と、サーバーの中で失敗した場合、サーバーは動き続け、ファイル名を示す警告を1回表示します。それ以降、その文書ではコメントを認識しません。編集しても、読み取りをやり直しません。範囲選択による翻訳は、その文書でも使えます。コメントをちょうど選択した場合は、コメントの記号を含む選択した文字列をそのまま送ります。文書を閉じて開き直すと、コメントをもう一度読み取ります。ほかの文書には影響しません。

### Rust

Rustは `//` と、入れ子にできる `/* ... */`、ドキュメントコメントの `///`、`//!`、`/** ... */`、`/*! ... */` に対応します。ドキュメントコメントと通常のコメントは、まとめて翻訳しません。1行目のシバンは除外します。

### JavaScriptとTypeScript

JavaScript、JSX、TypeScript、TSXは、`//` と `/* ... */` に対応します。JSDocの `/** ... */` と、`{/* ... */}` のようなJSXの中のコメントも含みます。モジュールと型宣言の規則は、`.mjs`、`.cjs`、`.mts`、`.cts`、`.d.ts` のようにファイル名から決めます。文字列、テンプレートリテラル、正規表現の中の文字列は、コメントとして扱いません。1行目のシバンは除外します。

構文解析を止める構文エラーがあると、それより後のコメントは抽出できません。

### C#

C#は `//`、`/* ... */`、`///`、`/** ... */` に対応します。XMLドキュメントコメントはタグ付きの訳文をホバーに表示し、タグ・属性の保持をモデルへ指示します。XML専用の整形表示や構造検証は行いません。構文エラーで判定が曖昧な範囲のコメントは対象から外します。

### CとC++

C/C++は通常コメントとDoxygen形式（`///`、`//!`、`/**`、`/*!`、末尾の説明用の `<` 付き形式）に対応します。`@param`などは本文に残し、コマンドと引数名の保持をモデルへ指示します。構文エラー範囲を飛ばし、マクロや入力途中の式より後でも認識できたコメントを抽出します。ただし、エラー範囲に引用符やブロックコメントの開始記号がある場合は、未閉鎖の内容をコメントと誤認しないようそこで停止します。

### Python

Pythonは `#` コメントと、モジュール・クラス・関数の先頭のドキュメンテーション文字列に対応します。通常の文字列・raw文字列・Unicode文字列、括弧付き、暗黙に連結した文字列を扱います。代入された文字列、f文字列（f-string）、バイト列リテラルは自動翻訳しません。ドキュメンテーション文字列の引用符と接頭辞を除き、エスケープや字下げはPythonとして評価せず原文のまま送ります。シバン（スクリプト先頭の `#!` 行）は除外します。構文エラー範囲を飛ばして抽出を続けます。ただし、エラー範囲に引用符がある場合は、未閉鎖文字列内の内容をコメントと誤認しないようそこで停止します。

### Go

Goは `//` と `/* ... */` に対応します。文字列、ルーン、raw文字列の中の文字列は、コメントとして扱いません。ディレクティブは、Go自身の `go/ast` と同じ規則で除外します。`//` の直後が `line `、`extern `、`export ` であるコメントと、`//go:build` や `//nolint:errcheck` のように、英小文字と数字の並びの後にコロンともう1文字続くコメントが該当します。閉じていない文字列とルーンは、その行の末尾で終わります。閉じていないraw文字列とブロックコメントは、それより後をすべて隠します。

### Ruby

Rubyは `#` のコメントと、`=begin` ... `=end` のブロックに対応します。1行目のシバンと、`__END__` より後はすべて除外します。

文字列、シンボル、正規表現、`%w[...]` などの `%` リテラル、`?#` などの文字リテラル、ヒアドキュメントの中の文字列は、コメントとして扱いません。文字列の `#{ ... }` の中にあるコメントは、コメントです。

`/`、`%`、`?`、`<<` がリテラルを始めるかどうかは、その前にあるものによって決まり、Rubyはその一部を、語がローカル変数かどうかで決めます。サーバーも同じ規則に従います。語は、次のいずれかの後、そのスコープの中でローカル変数になります。代入（`a, b = list` のような複数の代入先の1つとしても）、仮引数としての記述（既定値の中は除く）、`for` や `rescue => error` の変数としての記述、`in` の後のパターンでの束縛、`/(?<year>\d+)/ =~ text` のような `=~` の前の正規表現のグループによる命名です。`def`、`class`、`module` は外側の変数が見えないスコープを、ブロックとラムダは外側の変数が見えるスコープを始めます。たとえば `x /2 # note` の `# note` は、`x` がローカル変数ならコメントで、メソッドなら正規表現の一部です。

サーバーがたどるのは、これらの宣言のうち、よく使われる書き方です。`value => name` のように値の後の `=>` で束縛する変数は追いません。まれな書き方では、変数をメソッドと取り違えること、またはその逆があります。そのとき、`/`、`%`、`?`、`<<` の後のコメントが抜けたり、リテラルの一部をコメントとして扱ったりします。閉じていない文字列、リテラル、ヒアドキュメント、`=begin` は、それより後をすべて隠します。

### PHP

PHPでは、`<?php`、`<?=`、`<?` から `?>` までのコードにある `#`、`//`、`/* ... */`、`/** ... */` に対応します。`<?` は、PHPの既定の `short_open_tag` と同じくコードを始めます。HTMLなど、コードの外の文字列は読まないため、そこにあるHTMLのコメントはホバーによる自動翻訳の対象ではありません。

`#[` はコメントではなく属性を始めます。`?>` はコードとともに行コメントも終えます。文字列、ヒアドキュメント、Nowdocの中の文字列は、コメントとして扱いません。文字列の `{$ ... }` の中にあるコメントは、コメントです。`__halt_compiler` より後はすべて除外します。ただし、`$object->__halt_compiler` のようにプロパティや変数の名前である場合は除きます。閉じていない文字列、ヒアドキュメント、ブロックコメントは、それより後をすべて隠します。

### HTMLとCSS

HTMLは `<!-- ... -->` に対応します。`<script>` の中ではJavaScriptのコメントをJavaScriptのファイルと同じく読み、`<style>` の中ではCSSのコメントを読みます。スクリプトを読むのは、`type` が空、JavaScriptの型、`module` のいずれかの場合です。JSONなど、ほかのスクリプトは読みません。スクリプトの読み取りを止める構文エラーがあると、JavaScriptのファイルと同じく、そのスクリプトのそれより後のコメントは抽出できません。

タグとその属性値、`<textarea>`、`<title>` など、中にマークアップを持たない要素の中の文字列は、コメントとして扱いません。スクリプトはブラウザーと同じ箇所で終わります。中にある `<!--` と `<script>` によって、`</script>` がスクリプトの文字列の一部になる場合も同じです。

サーバーは、文書のツリーを作らずにHTMLを読みます。ツリーによってブラウザーの読み方が変わる箇所では、次の例外を除き、文書の本文と同じように読みます。`<![CDATA[` は、SVGとMathMLの中と同じく、それ以外の箇所でも `]]>` まで続きます。SVGとMathMLの中の `<script>` と `<style>` の文字列も、JavaScriptとCSSとして読みます。`<select>` の中でブラウザーが無視する `<textarea>` などの要素も、コメントを持たないものとして読みます。閉じていないコメントとタグは、それより後をすべて隠します。`<plaintext>` も同じです。

CSSは `/* ... */` に対応します。文字列と、引用符で囲まれていない `url( ... )` の中の文字列は、コメントとして扱いません。閉じていないコメントは、それより後をすべて隠します。

### JSON、YAML、TOML

JSONとJSONCは `//` と `/* ... */`、YAMLとTOMLは `#` に対応します。自動翻訳の対象はコメントだけです。キーや文字列の値を訳すときは、範囲を選択して `Translate selection to …` を使います。

文字列の中はコメントとして扱いません。JSONの文字列、YAMLの引用符付きの値とブロックスカラー（`|` と `>`）、TOMLの4種類の文字列が該当します。YAMLでは、`a#b` や `http://a/#frag` のように空白の後ろにない `#` もコメントではありません。

3形式とも字句を順に読みます。そのためJSONとTOMLでは、カンマの抜け、書きかけの値、閉じていない括弧といった構造のエラーがあっても、コメントを抽出できます。閉じていない1行の文字列は、その行の終わりまでを文字列として扱います。中身はコメントにならず、次の行以降には影響しません。JSONの閉じていないブロックコメントと、TOMLの閉じていない複数行の文字列は、それより後ろをすべて隠します。JSONでは、`'` で囲んだ部分も文字列と同じように飛ばします。TOMLでは、`don't` のように値の途中にある引用符も文字列の始まりとして扱います。YAMLでは、閉じていない引用符、字下げのタブ、キーにも値にもならない行など、最初のエラーで抽出を止めます。エラーより前のコメントは抽出できますが、エラーと同じ行か直前のコメントは取れないことがあります。

### シェルスクリプト

シェルスクリプトは `#` コメントに対応します。1行目のシバンは除外します。sh、Bash、zshのスクリプトを同じ方法で読みます。シェルによって読み方が違う箇所では、Bashの読み方に従います。Bashがデータとして読む部分をコメントとして扱うことはなく、代わりにコメントを対象から外します。

`#` は、行頭と、空白、`;`、`&` の後ろでコメントを始めます。`a#b` や `${x#y}` のように語の途中にある `#` はコメントではありません。引用符の中、ヒアドキュメントの中、`${ ... }` の中、`$(( ... ))` や `(( ... ))` などの算術式の中は、コメントとして扱いません。コマンド置換（`$( ... )` とバッククォート）の中のコメントは、置換が引用符の中にある場合も、コメントとして扱います。ヒアドキュメントの中の置換は読みません。

次のコメントは自動対象になりません。

- `(`、`)`、`|`、`<`、`>` の直後に、空白を挟まずに始まるコメント。Bashはここをコメントとして読みますが、zshでは `(#b)` や `(a|b)#` のようにパターンの一部になることがあります。
- バッククォートの中で、閉じるバッククォートで終わるコメントと、`\`、バッククォート、`$`、`"` の前に置いたバックスラッシュより後ろのコメント。

スクリプトの構造は検査しません。対応する `fi` のない `if` や、対応する `(` のない `)` は、何も隠しません。閉じていない引用符、`${`、`$((` は、それより後ろをすべて隠します。終わりの行がないヒアドキュメントも同じです。

シェルがその先をどう読むかを判断できない次の箇所では、抽出を止めます。そこより前のコメントは抽出できます。

- `${ command; }`。Bash 5.3はコマンドとして読み、それより古いシェルは読みません。
- 区切りの語が、単一引用符の外に `$` またはバッククォートを含むか、直後に `(` が続くヒアドキュメント。
- 外側の `$( ... )` を閉じる `)` の時点で、まだ本文が始まっていないヒアドキュメント。
- `&&`、`<<`、`$(` などの演算子を2行に分ける、行末のバックスラッシュ。
- 算術式ではなく2つのサブシェルを開く `((` のうち、括弧の対応が最初に取れる `)` までに `#`、`[`、`<<`、`case` のどれかを含むもの。
- `@(a|<<b)` のように、パターンの括弧の中にある `<<`。zshはここからヒアドキュメントを始めることがあります。
- `$( ... )` の中で、`(a)echo` のように括弧で囲んだ `case` のパターンの直後に語が続く箇所と、中の `case` の `esac` より前に置換を閉じる `)`。

### PowerShell

PowerShellは `#` コメントと `<# ... #>` のブロックコメントに対応します。1行目のシバンと `#Requires` の行は除外します。

`#` と `<#` は、行頭と、空白、`(`、`)`、`{`、`}`、`,`、`;`、`|`、`&` の後ろでコメントを始めます。これらの位置から始まった文字列とブロックコメントの直後でも同じです。バッククォートの直後の `#` はコメントを始めません。単一引用符の文字列、二重引用符の文字列、ヒア文字列、`${ ... }` の中は、コメントとして扱いません。`‘`、`’`、`“`、`”` など、PowerShellが引用符として受け付けるほかの記号は、`'` や `"` と同じように働きます。二重引用符の文字列の中にある `$( ... )` の中のコメントは、自動翻訳の対象になりません。

`a#b`、`$x#text`、`${x}#text` のように、空白を挟まずにほかの文字の後ろに続く `#` は、前後の文によって、コメントにも引数の一部にもなります。サーバーはどちらかを決めず、その行の `#` から後ろを自動対象から外します。`--%` の後ろも同じ扱いです。コマンドは、その行の残りを書かれたとおりに受け取ります。文字列の終わりにある `--%` も同じです。

見た目では終わっているのにPowerShellが読み進める次の箇所では、サーバーもPowerShellと同じように読みます。

- 二重引用符の文字列と二重引用符のヒア文字列の中で、`$( ... )` は最後の括弧まで、`${ ... }` は `}` まで続きます。途中の引用符や、ヒア文字列の終わりに見える行では終わりません。
- 引数の中と二重引用符のヒア文字列の中で、改行の前のバッククォートは改行をエスケープします。次の行は、トークンの先頭にも、ヒア文字列の終わりにもなりません。改行がCRLFの場合は、バッククォートがCRだけを取り込むので、次の行は通常どおりに働きます。
- 始まりの `@"` や `@'` と同じ行に空白以外の文字が続くヒア文字列は、その行の `"@` または `'@` で終わり、なければその行の終わりで終わります。
- `$$` と `@$` はそれぞれ1つの変数です。そのため、`$$(` や `@${` は `$( ... )` や `${ ... }` を始めません。

閉じていない文字列、ヒア文字列、`${` は、それより後ろのコメントを隠します。

PowerShellがその先をどう読むかを判断できない次の箇所では、抽出を止めます。そこより前のコメントは抽出できます。

- `$x=@"` のように、ほかの文字の直後にある `<#` とヒア文字列。
- `a=$( ... )` のようにほかの文字の直後にある `$( ... )` のうち、`#`、バッククォート、`${`、`--%`、ヒア文字列、括弧を含む文字列のどれかを中に持つもの。
- 引用符、`$`、`@`、`<`、`-`、`u{` の前にあるバッククォートのうち、``a`"b`` のように英数字、`_`、`.`、`\`、`+`、`#`、別のバッククォートの直後にあるものと、``-a=`"b`` のように `-name` を含む語の中にあるもの。``List`1`` のような型名の中と、コマンドのパラメーターの中のバッククォートは、次の文字をエスケープしません。
- `-name` を含む語の中、または語の途中の `@` の直後にある `${ ... }` のうち、引用符、`#`、バッククォート、`%` のどれかを中に持つもの。PowerShellは、ここの `{` をブロックの始まりとして読むことがあります。
- 同じ行の `[name,` の後ろにある引用符、`#`、`$`、`@`、`<`、バッククォートと、`(`、`)`、`{`、`}`、`;`、`|`、`&`。PowerShellはここをアセンブリ名として読むことがあり、その中ではこれらが何も始めません。`[name` の中のバッククォートも、英数字以外の前にあれば抽出を止めます。
- 同じ行の後ろに `|` か `&&` がある `--%` と、同じ行でそのような `#` や別の `--%` より後ろにある `--%`。
- 同じ行でそのような `#` や `--%` より後ろから始まり、次の行以降で終わる文字列、ヒア文字列、ブロックコメント、`${ ... }`。ほかの文字の直後にある `$( ... )` と、その行の終わりでほかの文字の直後にあるバッククォートも同じです。

### DockerfileとDocker Compose

Dockerfileでは、字下げの後の最初の文字が `#` である行がコメントです。`FROM a # text` のように行の途中にある `#` はコメントではありません。命令の継続行の間にあるコメント行は、コメントです。

パーサー指定は除外します。ファイルの先頭にあり、ほかのコメント、空行、命令のどれよりも前にある `# syntax=...`、`# escape=...`、`# check=...` の行が該当します。1行目のシバンも除外します。

ヒアドキュメントの行はコメントではありません。ヒアドキュメントは、`<<` または `<<-` で始まる語を持つ `RUN`、`COPY`、`ADD` の命令の後に続き、区切りだけの行で終わります。`<<-` では、その行の区切りの前にあるタブを無視します。区切りの行がないヒアドキュメントは、ファイルの末尾まで続きます。`<<<` と、引用符の中の `<<` は、ヒアドキュメントを始めません。

区切りの語は、BuildKitと同じ規則で読みます。語の全体または一部を囲む引用符は取り除きます。バックスラッシュは、引用符の外では取り除き、単一引用符の中では残します。二重引用符の中では、`"`、`$`、バックスラッシュの前にある場合だけ取り除きます。そのため、`<<"E\OF"` の区切りは `E\OF` です。エスケープ文字の指定は、この読み方を変えません。

BuildKitは、次の箇所をヒアドキュメントとして扱わず、後ろの行を命令やコメントとして読みます。サーバーはここもヒアドキュメントとして読み、両方の読み方でコメントになる行だけをコメントとして扱います。

- `<<- EOF` のように、`<<-` の後ろに空白を挟んで語が続く箇所。その語が区切りです。
- 閉じていない引用符や、BuildKitがエラーにする `${` を含む命令のうち、それより前に `<<` で始まる語があるもの。その語から区切りを読みます。
- `<<""` のような空の区切り。ヒアドキュメントは空行で終わります。
- `<<"a<b"` のように `<` を含む区切り。

区切りを読み取れない箇所では、抽出を止めます。閉じていない引用符やエラーになる `${` が `<<` の語または区切りの中にある場合と、`<<EOF${x:-y}` のように、その語が名前以外も含む `${name ... }` を持つ場合が該当します。そこより前のコメントは抽出できます。

Docker Composeのファイルは、[JSON、YAML、TOML](#jsonyamltoml)の規則でYAMLとして読みます。

## 言語サーバーの設定

C#ファイルでは、Zedの[C#言語拡張](https://github.com/zed-extensions/csharp)を導入してください。設定上の言語名は `CSharp` です。`languages.CSharp.language_servers` を明示している場合は、既存のC#サーバーに `"translation-lsp"` を追加します。RoslynやOmniSharpを置き換える必要はありません。

CとC++はZedに組み込まれています。言語サーバーを明示設定している場合は、`languages.C.language_servers` と `languages."C++".language_servers` の既存clangdに `"translation-lsp"` を追加します。

PythonもZedに組み込まれています。`languages.Python.language_servers` を明示設定している場合は、既存のPythonサーバーに `"translation-lsp"` を追加します。

GoとCSSはZedに組み込まれていて、HTML拡張はZedが既定で導入します。RubyとPHPのファイルでは、Zedの[Ruby拡張](https://github.com/zed-extensions/ruby)と[PHP拡張](https://github.com/zed-extensions/php)を導入してください。設定上の言語名は `Go`、`Ruby`、`PHP`、`HTML`、`CSS` です。これらの言語サーバーを明示設定している場合は、既存のサーバーに `"translation-lsp"` を追加します。

JSON、JSONC、YAMLはZedに組み込まれています。TOMLファイルでは、Zedの[TOML拡張](https://github.com/zed-extensions/toml)を導入してください。設定上の言語名は `JSON`、`JSONC`、`YAML`、`TOML` です。これらの言語サーバーを明示設定している場合は、既存のサーバーに `"translation-lsp"` を追加します。

Shell ScriptはZedに組み込まれていて、`.sh`、`.bash`、`.zsh`、`.bashrc`、`.zshrc` などのファイルを扱います。PowerShellファイルでは、Zedの[PowerShell拡張](https://github.com/zed-extensions/powershell)を導入してください。DockerfileとDocker Composeのファイルでは、両方の言語を提供するZedの[Dockerfile拡張](https://github.com/zed-extensions/dockerfile)を導入してください。設定上の言語名は `Shell Script`、`PowerShell`、`Dockerfile`、`Docker Compose` です。これらの言語サーバーを明示設定している場合は、既存のサーバーに `"translation-lsp"` を追加します。

Zedでは `.jsx` も `JavaScript`、`.tsx` は `TSX` の設定を使います。

どの言語にも共通する規則は[言語サーバーの一覧](configuration.md#言語サーバーの一覧)で説明します。
